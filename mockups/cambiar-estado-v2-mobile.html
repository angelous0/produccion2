Reglas de cálculo del "siguiente paso"

El frontend ya no decide qué mostrar. El backend devuelve, según la ruta del modelo + estado actual:

actual = "Para Lavanderia"
ruta = [Para Corte, Corte, Para Costura, Costura, Para Atraque, Atraque, Para Lavanderia, Lavanderia, Para Acabado, Acabado, Tienda]
obligatorio[Atraque] = false
→ siguientes_directos = [Lavanderia] // el inmediato tras "Para X" es siempre "X"
→ siguientes_salto = [] // no hay etapas opcionales por delante

En cambio, en pantalla 3:

actual = "Costura" (terminada, avance = 100%)
obligatorio[Atraque] = false
→ siguientes_directos = [Para Atraque]
→ siguientes_salto = [Para Lavanderia] // saltea la etapa opcional

Qué cambia respecto al sheet actual

  • Solo el siguiente posible según la ruta del modelo, no toda la lista.
  • 1 botón gigante si hay un solo siguiente. 2 botones si hay etapa opcional por delante (ej. Atraque).
  • Etiquetas claras en lugar de jerga: "Empezar Lavandería" en vez de "Lavanderia · Crea movimiento con fecha inicio = ahora".
  • Mini timeline arriba mostrando dónde estás en la ruta — Diana ve el contexto sin tener que recordar.
  • Bordados/Estampados u otros servicios que no están en la ruta del modelo nunca aparecen (ya pasa hoy en backend, solo confirmamos que se respeta).
  • "Otros estados" plegado por defecto — solo admin necesita forzar saltos o retrocesos. Y cuando lo abre, los estados están agrupados por "Hacia adelante / Hacia atrás" con pills.
  • Estado "ya terminado" (Tienda) muestra mensaje de finalización en vez de opciones, evita confusiones.

Cambios técnicos necesarios

  • Backend · nuevo endpoint o ampliar GET /registros/{id}/estados-disponibles para devolver una estructura más rica: 
    {
  "estado_actual": "Para Lavanderia",
  "siguientes_directos": [{ "nombre": "Lavanderia", "es_inmediato": true, "crea_movimiento": true }],
  "siguientes_salto":     [],
  "otros_adelante":       ["Para Acabado", "Acabado", "Tienda"],
  "otros_atras":          ["Costura", "Atraque"],
  "es_final":             false
}
  • Frontend móvil · reemplazar el sheet actual del componente CambiarEstadoSheet en RegistroDetalle.jsx por el nuevo diseño con:
    • Pregunta del título según el caso ("¿Avanzar el corte?" o "¿Hacia dónde va?")
    • Mini timeline visualizando la ruta
    • Botones grandes con etiquetas claras y subtítulo descriptivo
    • Sección "Otros estados (admin)" plegada
  • Mini timeline reutilizable · componente que pinta los pasos de la ruta con colores (done/current/skipped). Útil para reusar en el header del registro también (pantalla 4).

Pregunta para vos antes de implementar

Para el Atraque opcional: ¿la decisión de saltarlo es del modelo (algunos modelos tienen ruta con atraque y otros no) o del corte (siempre te aparece la bifurcación al salir de costura)?

  • Si es del modelo: en la ruta del modelo Atraque está o no está. Nunca hay bifurcación en el sheet — siempre 1 solo botón. La pantalla 3 no aplica.
  • Si es del corte: en la ruta el Atraque está marcado obligatorio: false. Al salir de costura el sheet ofrece los 2 botones (pantalla 3). Esto es lo que asumí.

Lo que cuente acá define el modelo de datos y la UX. Mi recomendación: si en la práctica los modelos saben de antemano si llevan atraque, voy con la primera (más simple). Si Diana decide caso a caso, voy con la segunda.
